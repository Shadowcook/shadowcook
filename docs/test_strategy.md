# Test strategy

## Purpose and current state

This document defines the test inventory for Shadowcook 2.0. Its primary purpose is to keep the HTTP API stable and to prevent regressions in the implemented cookbook, identity, authorization, and administration features.

The repository currently has no test runner, test scripts, or automated test files. `contracts/openapi.yaml` defines 119 API operations. `apps/api/src/app.ts` registers the Fastify routes directly; it does not currently expose a generated OpenAPI document at runtime. The contract must therefore be checked against the running API and not assumed to be generated by it.

Tests must use a dedicated disposable PostgreSQL database. They must never run `reset:dev-db`, `reset:shadowcook-db`, or otherwise modify a developer database. Test databases run migrations through `migrateDatabase`, are seeded only with explicit test fixtures, and are dropped or truncated after a test suite.

## Quality gates

The following commands should become mandatory for every change after the corresponding test layer exists:

| Gate                     | Scope                                | Required result                                                                                       |
| ------------------------ | ------------------------------------ | ----------------------------------------------------------------------------------------------------- |
| Static checks            | existing TypeScript and Astro checks | `pnpm check` succeeds                                                                                 |
| Unit tests               | pure API and web functions           | all pass                                                                                              |
| API integration tests    | Fastify routes with PostgreSQL       | all pass against an isolated database                                                                 |
| API contract tests       | every implemented OpenAPI operation  | route, method, security, status code, media type, and JSON schema agree with `contracts/openapi.yaml` |
| Browser end-to-end tests | critical user journeys               | all pass against isolated API and web instances                                                       |
| Migration tests          | new database and upgraded database   | migrations are repeatable and preserve expected data                                                  |

The first implementation should add a root `pnpm test` command and separate commands for `test:unit`, `test:api`, `test:contract`, `test:e2e`, and `test:migrations`. The exact runner is an implementation decision; a TypeScript-native unit/API runner with Fastify `inject`, PostgreSQL integration tests, and a browser runner are required capabilities.

## Test data and actors

Reusable fixtures must create only the data needed by each test and must make all public IDs, slugs, clock values, and expiry timestamps deterministic where the assertion needs them.

The common fixture set should contain:

- an instance administrator;
- an owner, editor, and viewer in tenant `alpha`;
- an authenticated non-member and an unauthenticated request;
- an owner and a viewer in separate tenant `bravo`;
- a disabled user, a deleted user, a disabled tenant, and an expired session/token where needed;
- a public, members-only, private, discoverable, and unlisted published recipe;
- a recipe with an active draft, at least two published/archived revisions, multiple variants, categories, steps, ingredient usages, and a share link;
- instance-owned and tenant-owned ingredients and units, including aliases and usages that prevent deletion;
- a service account with a least-privilege tenant role and a separate AI-context grant.

Each fixture helper must return the identifiers and credentials it creates. Tests must not depend on the development accounts or development content seed.

## Priority 0: invariants and security boundaries

These are the first API integration tests. They protect data isolation and the architectural invariants in `docs/ARCHITECTURE.md`.

| Area                           | Required assertions                                                                                                                                                                                                                                                                                                                      |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Authentication                 | Missing, malformed, expired, revoked, and disabled session/bearer credentials return the documented authentication failure. Login creates an HttpOnly session; logout and deactivation invalidate it. Password-change-required sessions can reach only the permitted endpoints.                                                          |
| Instance authorization         | A tenant role never grants instance administration. A service account never receives instance access. Each `/admin` operation rejects unauthenticated users and authenticated non-administrators.                                                                                                                                        |
| Tenant isolation               | A principal from `alpha` cannot read, mutate, list, or infer resources in `bravo`, including recipes, drafts, categories, users, ingredients, units, service accounts, tokens, share links, and AI-context scopes. Test both UUID/public-ID and slug paths.                                                                              |
| Tenant authorization           | Owner, editor, viewer, and a least-privilege service account have exactly the documented permissions. A request with one permission must not imply another permission.                                                                                                                                                                   |
| Visibility and discoverability | Test the complete matrix of anonymous, non-member, member, and visibility-management principal against `PUBLIC`, `MEMBERS_ONLY`, and `PRIVATE`; repeat with `DISCOVERABLE` and `UNLISTED`. Unlisted recipes remain directly readable only to an allowed caller and are absent from lists.                                                |
| Draft/read separation          | General reader endpoints never expose drafts. Draft and revision endpoints reject callers without their dedicated permissions. A published private recipe remains private. Publishing a recipe does not itself change its audience.                                                                                                      |
| Recipe revision lifecycle      | A recipe has at most one draft; edit operations do not publish; publishing atomically promotes the draft, archives the former published revision, increments the version, and leaves published snapshots unchanged. Metadata-only updates do not create a revision.                                                                      |
| Variants                       | Every recipe has exactly one visible default variant. Variant step membership stays within the recipe revision. Variant deletion fails when steps still belong to it; reader variant resolution does not expose invisible variants.                                                                                                      |
| Share links                    | Token plaintext is returned only at creation; the stored data is a verifier. Valid links read the current published default variant only. Revoked, expired, unknown, and malformed links fail without exposing recipe metadata. Creating, listing, and revoking links requires `recipe:visibility-update`.                               |
| Service accounts               | A bearer token works only while the token, service account, principal, membership, and role are active. Token creation returns plaintext once; list responses return metadata only. Revocation and disabling immediately stop access and update no unrelated tenant.                                                                     |
| AI context                     | Bootstrap links are single-use, expire after 30 minutes, use `no-store` and `no-referrer`, and issue a scoped reader token. Expired/revoked access fails. Tenant, category-subtree, and recipe scopes include only permitted resources. Reader credentials are rejected by ordinary API endpoints and reader endpoints accept no writes. |
| Registration and invitations   | Honeypot, rate-limit, Turnstile configuration, generic resend/reset responses, expiry, single-use verification, and atomic account/tenant/role creation are exercised. Invitation acceptance distinguishes a new account from an existing account with the wrong and correct authenticated email.                                        |

For each access-controlled endpoint, at least one success case and these negative cases are required where applicable: no credential, authenticated but unauthorized credential, wrong tenant, disabled resource, invalid input, and absent resource. Assertions must include the documented response code and error `code`, not only the HTTP status.

## Priority 1: API contract coverage

Every `operationId` in `contracts/openapi.yaml` needs an automated example. Contract coverage is grouped by route family below so that additions to the contract visibly add test work.

| Route family                            | Operations to cover                                                                                                       | Essential scenarios                                                                                                              |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| Health and public configuration         | `/health`, registration configuration, password requirements, authentication methods, legal documents                     | stable public response shape; configured and unconfigured registration/Turnstile state                                           |
| Authentication                          | login, session, logout, password change, password-reset request/complete, email-code request/verify                       | cookie attributes, generic anti-enumeration responses, entropy/rate/expiry/single-use rules                                      |
| Public registration                     | registration, resend, verification                                                                                        | valid path, disabled registration, validation failure, duplicate/expired/consumed token, slug collision                          |
| Instance settings                       | registration, authentication, mail, front page, legal documents                                                           | administrator-only access, validation boundaries, encryption-safe response shape, SMTP test failure/success handling             |
| Instance catalogues                     | `/admin/units*`                                                                                                           | CRUD, use-count deletion guard, duplicate names, compatible and incompatible unit conversion                                     |
| Instance users and tenants              | `/admin/tenants*`, `/admin/users*`, instance roles and invitations                                                        | role assignment limits, disable/delete/reset effects, tenant creation SMTP precondition, tenant slug validation and uniqueness   |
| Cookbook reader                         | `/cookbook`, accessible tenants, recipe detail, shared-recipe resolver                                                    | audience/visibility matrix, pagination/filter ordering, feature/front-page rules, category membership, visible variants          |
| Tenant settings and categories          | recipe policy and category CRUD/move routes                                                                               | inherited versus overridden policy, reserved/duplicate slugs, tree reparenting, adjacent ordering, guarded deletion              |
| Recipe editing and history              | draft list/create/read/update, metadata, publishing, revisions, draft steps, variants, overrides, editor catalogue/search | all lifecycle, optimistic-concurrency behaviour when present, stable keys, validation, pagination/filtering, immutable snapshots |
| Tenant catalogues                       | tenant ingredients, aliases, consolidation actions, and units                                                             | tenant-only ownership, on-the-fly creation, all reassignment outcomes, usage-aware deletion                                      |
| Tenant users                            | tenant-user list, invitation, role replacement                                                                            | tenant-scoped membership, only tenant-local roles accepted, existing-user email match                                            |
| Service accounts and recipe share links | all service-account/token and share-link routes                                                                           | least privilege, one-time token visibility, lifecycle changes, expiry/revocation                                                 |
| AI contexts                             | context creation, bootstrap exchange, overview, recipe, revisions, revision, draft reader paths                           | one-time exchange, headers, duration boundaries, scope filtering, read-only bearer acceptance                                    |

Contract tests must validate:

- every documented method/path pair resolves, and no route required by a client is omitted;
- path/query parameters and request bodies accept valid boundary values and reject invalid ones;
- each documented success and error status has the documented content type and required JSON fields;
- enum values, nullability, date-time values, IDs, and pagination fields match the schema;
- documented cookie and bearer security requirements are actually enforced;
- API error bodies use the contract's `ApiError` form;
- implementation-only fields, secrets, password hashes, verification tokens, session tokens, and database IDs never occur in a response.

Schema validation should validate actual JSON responses against the OpenAPI schemas. In addition, keep hand-written semantic assertions: schema validation cannot determine whether a caller received another tenant's recipe or whether a token was exposed only once.

## Priority 2: database and migration tests

Migration tests use a freshly created disposable PostgreSQL database, never a shared development schema.

- Apply all migrations to an empty database and verify the resulting tables, constraints, indexes, triggers, functions, seed records, and expected permissions.
- Run `migrateDatabase` a second time and verify that no migration is rerun and the migration ledger is unchanged.
- Start from a database at each prior released migration state, apply the remaining migrations, and verify preserved tenant, user, recipe, revision, and catalogue data.
- Verify failure and rollback for a deliberately failing migration in a test-only migration fixture: no partial schema/data changes and no ledger entry remain.
- Verify unknown applied IDs and checksum mismatches stop migration before API startup.
- Verify advisory-lock behavior with two concurrent migration attempts.
- Verify UTC timestamps for migration ledger, sessions, tokens, invitations, revisions, share links, and audit-relevant timestamps.
- Test database-enforced constraints that protect application assumptions: tenant-local slug uniqueness, reserved slugs, unique/default variant rules, revision-status rules, foreign keys, enum/check constraints, and deletion guards.

The legacy-import workspace needs separate integration fixtures based on a minimal legacy HSQLDB source. Test dry-run rollback, empty-target enforcement, deterministic slug collisions, unit/special-entry mapping, authored usage-note preservation, and one published default variant per imported recipe.

## Unit tests

Unit tests are appropriate only for deterministic code without PostgreSQL or HTTP transport. The current high-value candidates are:

- `apps/api/src/auth/password.ts`: normalization, entropy threshold, and password-hash verification cases;
- `apps/api/src/auth/session.ts`, `email-code.ts`, and `password-reset.ts`: token hashing, parsing, expiry inputs, and cookie parsing;
- `apps/api/src/security/encryption.ts`: round trips, wrong-key failure, and ciphertext format;
- parsers and validators inside route modules: UUIDs, slugs, decimals, page values, payload shapes, and unit conversion input;
- `apps/web/src/features/cookbook/model/routing.ts`: root/category/recipe/variant deep links, invalid paths, URL decoding, and category ancestry;
- `apps/web/src/features/cookbook/model/shopping-list.ts`: aggregation by ingredient, unit, and optionality; exact decimal addition; zero trimming; special/free-text exclusion;
- `apps/web/src/features/cookbook/server/recipe-structured-data.ts`: JSON-LD fields, localized unit presentation, absent optional fields, and no trailing decimal zeroes;
- `apps/web/src/lib/password-entropy.ts`, locale lookup, unit localization, Markdown rendering configuration, and API-error mapping.

Tests for pure functions should avoid snapshot-only assertions. Assert the returned values and edge cases explicitly.

## Browser end-to-end tests

Browser tests cover wiring between server rendering, client hydration, proxying, session cookies, deep links, and localized UI. They should run against test-specific API and web ports with an isolated test database.

The initial browser suite should cover:

1. Anonymous visitor opens a public cookbook, category, root recipe URL, category recipe URL, and visible variant URL; the initial HTML contains recipe content, semantic links, and Recipe JSON-LD without JavaScript.
2. Anonymous visitor cannot open a private/members-only recipe or a management URL; a protected URL redirects to login and preserves the validated `next` path.
3. Login, logout, session restoration, and a password-change-required redirect work through the web proxy.
4. Owner creates a draft, categories, steps, usages, and variants; publishes it; sees it in the reader; then edits it and confirms the old published page remains stable until the next publish.
5. Owner changes visibility/discoverability and share-link state; a second browser context observes precisely the allowed reader result.
6. Tenant management navigation, category ordering, pagination/filtering, and recipe deep links remain links that can open in a new tab.
7. English and German UI rendering uses localized UI text, error messages, metadata, labels, and accessibility text while authored recipe content remains unchanged.
8. Instance administrator manages a tenant/user/catalogue record; a tenant owner manages only their own tenant resources.

Visual regression testing is optional after these semantic journeys are stable. If it is introduced, cover the public recipe page, cookbook navigation, recipe editor, and the administration shell at desktop and mobile widths.

## Execution order

Implement the suite in the following order. Each stage is independently useful and should be made green in CI before the next stage expands it.

1. Add test commands, disposable PostgreSQL fixture infrastructure, API factory helpers, deterministic clock/token helpers, and a small unit-test foundation.
2. Add health, authentication, authorization, tenant-isolation, visibility, draft/read separation, and recipe publish lifecycle integration tests.
3. Add OpenAPI response/schema validation and one canonical success/error test for every operation family; expand until all 119 operation IDs are covered.
4. Add catalogue, category, unit-conversion, tenant-user, invitation, registration, service-account, share-link, and AI-context integration flows.
5. Add migration, seed, and legacy-import integration tests.
6. Add the listed browser journeys, then run them in CI on every change that affects `apps/web`, `apps/api`, `packages/db`, or `contracts/openapi.yaml`.

## Test maintenance rules

- A changed API route, request, response, authentication requirement, or error code changes both `contracts/openapi.yaml` and its contract test in the same change.
- A reported regression receives a focused test before or together with its fix.
- New permissions, roles, tenant-owned resources, visibility states, or token types extend the shared actor/authorization matrix before feature-specific tests are added.
- New migrations add fresh-install, upgrade, repeatability, and rollback coverage.
- Browser tests assert user-visible behaviour and accessibility semantics, not implementation-specific React or Astro details.
- Tests must use UTC assertions for persisted/logged timestamps and must not assert local-time formatting except in explicit UI locale/time-format tests.
