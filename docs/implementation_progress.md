# Shadowcook 2.0 implementation progress

Implemented capabilities are documented in [ARCHITECTURE.md](ARCHITECTURE.md). Unimplemented capabilities and feature ideas are collected in the [roadmap backlog](roadmap.md#backlog).

### Product landing page and cookbook discovery

- `/` serves the localized public product landing page with SSR marketing content, original branding, a labeled example using the shared recipe-step renderer, responsive sections, localized metadata, and links to registration and Explore (architecture: [Cookbook navigation, reading, and editing](ARCHITECTURE.md#cookbook-navigation-reading-and-editing)).
- Deployment packages include Apache and Nginx proxy examples with commented instructions and optional routing of `/`, `/landing`, and `/landing/*` to an operator-provided landing website. The default continues to serve the built-in page (architecture: [Deployment](ARCHITECTURE.md#deployment)).
- `/explore` retains the existing tenant selection, My Cookbooks, search, pagination, shuffle, and stored overview settings. Header navigation and login defaults point to Explore; validated deep-link login destinations and logout behavior are retained.
- The API reserves `explore` and `landing` through its existing central slug policy. The available local database contains neither tenant slug. No database schema or API payload changes are introduced. Other installations require the documented preflight collision check.
- Unit, API and built-Astro integration coverage includes redirect validation, slug rejection, localized root HTML, Explorer classification, system routes, and short cookbook/category/recipe/variant URLs.

## Completed architecture features

### Public recipe authoring skill

- Public versioned skill, Draft-07 recipe JSON schema, format and icon guides, simple and variant examples, and a Python structural/semantic validator are exposed through the API and included in the downloadable skill ZIP (architecture: [Public recipe authoring skill](ARCHITECTURE.md#public-recipe-authoring-skill)).
- AI-sharing manifests link absolute skill, schema, example and ZIP URLs with the public API prefix and credential-free authoring instructions. Context grants remain read-only.
- The portable document uses independent ingredient/unit keys, explicit variant step membership, optional source identities and recipe lineage, and exact decimal conversion data. Authenticated federation import and trusted reusable source mappings remain unimplemented.
- Skill instructions, format/icon guides and the variant example keep the left column strictly technical and compact. Prose and complete warnings belong in step instructions or dedicated warning steps; special-entry markers can omit notes (architecture: [Public recipe authoring skill](ARCHITECTURE.md#public-recipe-authoring-skill)).
- Skill instructions and the format guide require notes to agree with authoritative structured quantities, exclude redundant or competing same-unit amounts and approximation qualifiers, and include this consistency check in manual validation (architecture: [Public recipe authoring skill](ARCHITECTURE.md#public-recipe-authoring-skill)).
- Public-resource, archive and schema unit tests cover resource links, ZIP contents and structural rejection. AI-context integration tests verify credential-free resource retrieval through the web proxy. `pnpm test:skill` runs the Python validator's positive, negative and CLI tests with the skill's Python dependencies installed.

### Recipe JSON upload and draft import

- The Import Recipe action appears only in recipe management, above and to the right of Create Recipe; Create Recipe appears below on the left (architecture: [Recipe JSON upload and draft import](ARCHITECTURE.md#recipe-json-upload-and-draft-import)).
- Page-wide JSON-file drops show a drag overlay, switch to file input and automatically validate the file before opening the recipe overview. The source step shows the filename. Localized errors cover multiple files, non-JSON files and the shared size limit; reading and submission block further drops (architecture: [Recipe JSON upload and draft import](ARCHITECTURE.md#recipe-json-upload-and-draft-import)).
- A deep-linkable cookbook import wizard accepts a JSON file or pasted JSON, validates the portable v1 format, and guides users through an informational overview, editable title/URL/category/variant name and slug head data, and ingredient/unit assignment tables with Next, Previous and Finish controls. Title edits appear in the overview and imported draft; titles require non-whitespace text and are limited to 240 characters. Variant names set to the locale default or left empty reset the variant slug to `default`; variant slugs remain editable and require valid, unique values. Choices survive backward navigation (architecture: [Recipe JSON upload and draft import](ARCHITECTURE.md#recipe-json-upload-and-draft-import)).
- Assignment comboboxes show the permitted new-entry choice first, integrate catalogue search, retain original-entry suggestions above filtered existing entries, support keyboard navigation, and retain selected search results between steps. Existing ingredient mappings provide an explicit Add as alias checkbox gated by `ingredient:update`; alias additions participate in the import transaction. New-entry selections clear and disable the alias checkbox.
- Cookbook-local ingredient names and aliases and visible unit definitions/translations provide ranked suggestions. Users can search existing entries or explicitly create new ones when permitted. Unknown unit definitions require selection; incompatible known definitions are rejected.
- Import revalidates selections and stores all new catalogue entries, recipe content, variants, metadata and contributor attribution atomically as a draft. Source identities remain unverified, known lineage is retained, and source records are included in cookbook exports. Full cookbook ZIP import and authenticated federation synchronization remain unimplemented.

### Recipe metadata and dietary classification

- Calories per serving are calculated only when both required values exist. Missing input is valid; empty fields and unavailable derived values are hidden. Created and last-published-change timestamps are automatic and read-only.
- Explicit vegan, vegetarian, and omnivorous classifications support hierarchical cookbook search, combined text filtering, deep links, browser history, and optional MCP search filters. Unclassified recipes appear only without a diet filter.
- Recipe cards and regular and shared recipe detail views show a green leaf for vegan recipes and a green egg for vegetarian recipes beside the title, with localized tooltips and accessible names. Detail views and PDF covers include the localized diet name beside the matching symbol. Recipe summary responses include the published dietary classification (architecture: [Cookbook navigation, reading, and editing](ARCHITECTURE.md#cookbook-navigation-reading-and-editing)).
- A BETA-2 migration adds constrained nullable revision columns. Draft copying, publication, history, sharing, AI readers, cookbook exports, content-seed exports, and the OpenAPI contract include the metadata.

### Content reports and moderation tickets

- Recipe and cookbook report controls appear inside small ellipsis action menus with link copying and permitted recipe actions. Cookbook overview cards have no report controls. User report controls appear only beside visible user names in tenant-user management. Shared report dialogs have neutral English/German text and require reasons and descriptions (architecture: [Content reports](ARCHITECTURE.md#content-reports)).

- A BETA-2 migration adds normalized report, notification, and instance-report-setting tables. The OpenAPI contract includes report submission, reportable-user selection, settings, ticket management, and the cookbook public identifier.

The new deployment environment template derives image tags from the project name; existing project and image defaults remain supported. Each service runs as one container per project; existing network and database volume names are retained when the project name stays the same (architecture: [Deployment](ARCHITECTURE.md#deployment)).
- Both Docker Compose deployment variants reuse existing local API and web images during normal startup and apply changed runtime `.env` configuration through container recreation. Commit updates and public-origin changes use explicit image builds; missing application images are built on startup (architecture: [Deployment](ARCHITECTURE.md#deployment)).
- PostgreSQL uses the initial normalized schema for tenants, principals, roles, catalogues, recipes, immutable revisions, media, audit events, cooking sessions, sharing, federation upstreams, and mappings. The initial schema migration is maintained as a UTC timestamp-prefixed SQL file.

- The automated-test foundation provides a sequential root test runner with per-suite and overall pass/fail summaries, deterministic clock/token helpers, Fastify API factory helpers, and isolated PostgreSQL integration fixtures. API, contract, and migration suites run against a fresh disposable Docker PostgreSQL container on a random loopback port; unit tests cover password, token, cookie, email-normalization, and encryption functions.

- The API exposes the health endpoint and documented API contract.
- Development startup loads the base JSON seed and then an optional local JSON content seed for ingredients, categories, recipes, revisions, variants, steps, ingredient usages, and their referenced catalogues.
- The tracked initial-deployment seed creates localized instance-owned units.

- Development ingredient cleanup exports all catalogued content-seed ingredients to a four-column CSV and ingests validated renames, recipe-note modifiers, and aliases back into the content seed.

### Authentication, authorization, and administration

- Password-login failures use persistent IP-only limits of ten failures in a rolling 15-minute window, concurrency-safe PostgreSQL transactions, a localized limit message, and documented `LOGIN_RATE_LIMITED`/`Retry-After` responses. Account names do not define limit buckets; successful logins do not count (architecture: [Bootstrap administrator and password recovery](ARCHITECTURE.md#bootstrap-administrator-and-password-recovery)).
- Web and API runtimes support explicit trusted proxy ranges. The web HTTP entrypoint and development proxy sanitize visitor IPs from the socket and trusted chain, and the Apache example replaces incoming forwarding headers. Both Compose variants configure proxy trust (architecture: [Deployment](ARCHITECTURE.md#deployment)).
- Password changes atomically preserve the current session and revoke other sessions belonging to the same account, with locked credential revalidation and targeted API/proxy regression coverage (architecture: [Bootstrap administrator and password recovery](ARCHITECTURE.md#bootstrap-administrator-and-password-recovery)).

- Instance-user, cookbook-user, and cookbook-owner invitations collect first name, last name, and display name from the invited person when creating an account. Inviter forms require only the recipient email address as personal information. Existing-account acceptance preserves the profile; cookbook-owner profile validation preserves the email code on invalid names (architecture: [Instance administration](ARCHITECTURE.md#instance-administration), [Access data model](ARCHITECTURE.md#access-data-model)).

- Public registration requires first name, last name, and display name, stores them until email verification, and transfers them to the account. Account settings provide localized editing of all three names through authenticated profile endpoints, including immediate display-name updates in the header (architecture: [Registration and account settings](ARCHITECTURE.md#registration-and-account-settings)).

- Human password authentication, email-code authentication, opaque HttpOnly sessions, password-change enforcement, password resets, and bootstrap administration are implemented. Instance administrators configure a 1-to-256-bit minimum estimated password entropy, with a local threshold-centred progress test; the default is 60 bits. The zxcvbn-ts estimate recognizes common words, sequences, repetitions, l33t substitutions, and keyboard patterns, while fully random character sequences use character-pool entropy. Browser indicator calculations are debounced by 200 milliseconds and analyze at most the first 64 characters. Registration, password-change, password-reset, and account-invitation forms show the same local threshold-centred progress indicator. All password-entry fields provide a localized show-or-hide control, and password-change completion does not require repeated entry. Entropy validation applies outside development only.
- Tenant invitation acceptance starts an invited account session, directs it to the assigned cookbook, and supports first-password completion without a current-password field and with localized repeated-password validation. Tenant-user invitations support invited existing accounts through an authenticated email-match check and add their existing principal to the selected cookbook membership.
- One-time email codes are hashed, expiring, rate-limited, and delivered through configured SMTP.
- SMTP configuration is permission-gated, encrypts stored passwords, and supports test delivery.
- Tenant creation is disabled until SMTP delivery is configured, with a localized configuration requirement, server-side `SMTP_REQUIRED` enforcement, and a localized mail-delivery failure message for owner invitations.
- The authorization model includes canonical permissions, instance roles, tenant roles, tenant memberships, tenant-scoped role assignment, and the initial `Owner`, `Editor`, and `Viewer` roles.
- Instance administration lists every website user and manages global instance roles, user deactivation, password resets, and soft deletion. Tenant membership and tenant-role assignment require the tenant-scoped `tenant:manage` permission.
- Instance administration provides deep-linkable dashboards and tenant, user, authentication, SMTP, and unit management.
- Middleware protects administration and tenant-management routes, preserves validated post-login navigation, and the web client validates restored sessions with the API.
- Protected tenant-management and instance-administration pages server-resolve their access state before rendering without a session-check loading screen.
- A sticky global head bar is server-seeded with the current session on every web route, then client-validated, and provides localized sign-in, authenticated-user, authorized administration, and sign-out actions, including invitation acceptance routes.
- The global head bar displays only its logo and icons with localized tooltips and accessible names. The user dropdown shows the account display name and email before its options; the session API supplies `displayName`. Shared dropdowns support outside-click dismissal and Escape with focus restoration (architecture: [Cookbook navigation, reading, and editing](ARCHITECTURE.md#cookbook-navigation-reading-and-editing)).
- Instance-administration UI code is organized under `apps/web/src/features/admin`.
- Tenant owners can create service accounts, assign existing tenant roles, issue one-time-view opaque bearer tokens, inspect token lifecycle metadata, revoke tokens, and disable service accounts.
- Bearer-token authentication resolves service accounts through their active tenant membership and permissions; recipe and recipe-draft APIs therefore support AI and automation clients without a separate agent API.
- The authenticated remote MCP endpoint exposes provider-neutral recipe search and draft-editing tools for compatible AI clients. It cannot publish or delete recipes.
- All MCP tools share portable nullable input schemas with separate `anyOf` branches and preserved UUID formats, required fields, and closed objects. Schema unit tests and authenticated `tools/list` / `tools/call` integration tests cover explicit nulls, omitted nullable fields, and clearing recipe summaries.

- MCP recipe assistants can search and create tenant-owned ingredients and units when the authenticated tenant role grants the respective permissions. Instance-owned catalogue records remain unavailable to MCP writes.
